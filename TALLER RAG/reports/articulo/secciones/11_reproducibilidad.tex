\section{Reproducibilidad}
\label{sec:reproducibilidad}

\subsection{Hardware y software}

El sistema se ejecut\'o en una estaci\'on con Ryzen 9 5950X, 31 GB de RAM y una GPU AMD Radeon RX 9070 XT de 16 GB con ROCm 7.2.4. La capa de datos (etcd, MinIO y Milvus 2.6.6) corre en un servidor de la red local con 16 n\'ucleos y 62 GB de RAM; el API, el embedding y el generador siguen en la estaci\'on. El API se conecta a Milvus por LAN en \texttt{http://192.168.1.100:19530}; el stack de datos se despliega con Docker Swarm y la aplicaci\'on con Compose. Los contenedores usan Python 3.12, PyTorch 2.10 con ROCm, FastAPI, Streamlit y Ollama. RAGAS 0.4.3 y LangChain 0.3 corren en un contenedor aparte con Python 3.12 y \texttt{BAAI/bge-m3} en CPU.

\subsection{Comandos}

El stack completo se levanta con un comando:

\begin{verbatim}
make all-up
make ps
curl http://localhost:8010/health
\end{verbatim}

\texttt{make all-up} construye y arranca el stack completo (etcd, MinIO, Milvus, Solr, Ollama, API y frontend), espera a que la API est\'e sana, descarga \texttt{gemma4:e4b} y \texttt{gemma2:2b}, ingiere el Parquet, construye la colecci\'on dispersa e indexa Solr en texto y vectores. El servicio \texttt{prewarm} carga el generador, el embedding y el reordenador cuando la API est\'a sana. El apagado deja los vol\'umenes intactos:

\begin{verbatim}
make all-down
\end{verbatim}

La capa de datos del servidor se despliega con el stack de Swarm y el core de Solr con su esquema:

\begin{verbatim}
scripts/deploy_solr.sh
\end{verbatim}

El grafo se construye desde el Parquet con \texttt{make graph-build}, que ejecuta \texttt{build\_graph} por lotes de 1000. La evaluaci\'on se corre contra un conjunto y se registra como experimento de Langfuse:

\begin{verbatim}
make eval-langfuse RUN=extra-30
\end{verbatim}

El conjunto y el destino se pasan con los flags del script:

{\footnotesize
\begin{verbatim}
python -m src.scripts.eval_langfuse \
  --silver eval/silver/silver_extra.jsonl \
  --dataset silver-extra --run extra-30
\end{verbatim}
}

La configuraci\'on desplegada se fija en \texttt{.env}:

\begin{verbatim}
RETRIEVER=hybrid_boost
PROMPT_VERSION=v3
TRANSLATION=1
LIST_EXTRACTION=1
NUMERIC_VERIFICATION=0
QUERY_EXPANSION=0
CANDIDATE_GUARANTEE=0
\end{verbatim}

\subsection{Demo p\'ublica}
\label{sec:demo}

La aplicaci\'on qued\'o publicada en \url{https://tallerrag.hardwareelite.online} mediante un t\'unel de Cloudflare. El t\'unel \texttt{taller-rag} se cre\'o con la API de Cloudflare, con configuraci\'on remota y un solo ingress: el hostname p\'ublico apunta a \texttt{http://localhost:8501}, el puerto del frontend, y el resto de las rutas devuelve 404. El DNS es un CNAME proxied a \texttt{<id>.cfargotunnel.com}. El conector corre como un contenedor m\'as (\texttt{docker-compose.tunnel.yml}, red de host y \texttt{restart: unless-stopped}) y lee el token de \texttt{docker/cloudflared/.env}, que no se versiona. La p\'agina no tiene autenticaci\'on: es una demo abierta del taller, no un despliegue de producci\'on.

La aplicaci\'on corre en la estaci\'on y el frontend habla con el API por \texttt{localhost:8010}; el API usa el Milvus y el Solr del servidor (\texttt{192.168.1.100}) y el generador y el embedding locales. Cloudflare publica dos hostnames: \texttt{tallerrag}, que sirve la interfaz, y \texttt{langfuse}, que sirve el panel de trazas; la API no queda expuesta. La barra lateral enlaza el panel y cada respuesta enlaza su propia traza. La Figura~\ref{fig:demo} muestra una consulta real hecha por la URL p\'ublica.

\begin{figure*}[t]
\centering
\includegraphics[width=0.9\textwidth]{demo_publica.png}
\caption{Demo p\'ublica: consulta real por \texttt{tallerrag.hardwareelite.online}. La respuesta cita siete de las diez evidencias recuperadas, la compuerta acepta la pregunta con probabilidad 0,919 y la interfaz muestra la ruta y la latencia. El bot\'on \textit{Ver traza en Langfuse} abre la traza de esa respuesta en el panel p\'ublico. La primera consulta paga la carga del reordenador; en caliente, la misma pregunta tarda 4,5 s.}

La verificaci\'on fue: \texttt{curl} al hostname devuelve 200 con el HTML de Streamlit, el t\'unel registra cuatro conexiones QUIC y un navegador headless completa la pregunta y recibe la respuesta con citas. La primera consulta por la URL p\'ublica tarda entre 10 y 12 s porque carga el reordenador; con el modelo caliente, la misma pregunta tarda 4,5 s (60 ms de recuperaci\'on y el resto de generaci\'on).

\subsection{Observabilidad y grafo}

El stack de observabilidad se despliega en el servidor y se detiene sin borrar vol\'umenes:

\begin{verbatim}
make obs-up
make obs-down
\end{verbatim}

\texttt{make obs-up} usa el compose de observabilidad con su archivo de entorno no versionado. Las capturas de Langfuse y Neo4j se generan con \texttt{scripts/capture\_firefox.py} y Firefox headless. El modo del recuperador se elige por petici\'on con el campo \texttt{retriever} (\texttt{hybrid\_union}, \texttt{hybrid\_boost}, \texttt{graph\_hybrid}, \texttt{solr}).

\subsection{Datos}

El corpus completo no se publica por derechos de las fuentes. Se incluyen el silver, las anotaciones, la muestra del piloto y los Parquet de evaluaci\'on necesarios para reproducir las m\'etricas. Los Parquet se versionan con Git LFS (\texttt{*.parquet filter=lfs}); despu\'es de clonar hay que ejecutar \texttt{git lfs pull} para materializarlos. Las cifras de este art\'iculo se pueden verificar contra esos artefactos sin volver a descargar el corpus.
